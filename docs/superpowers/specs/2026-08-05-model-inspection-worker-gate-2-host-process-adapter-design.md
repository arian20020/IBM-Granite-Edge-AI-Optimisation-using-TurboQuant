# Model Inspection Worker Gate 2 - Hardened Host and Process Adapter Design

**Status:** Approved conversational design; written specification awaiting user review  
**Date:** 2026-08-05  
**Target branch:** `feature/model-inspection-worker-host`  
**Stacked base branch:** `feature/model-inspection-runtime-integration`  
**Required base commit:** `0d50f27405d66be944e1352284b68928ae228e74`  
**Target platform:** Windows x64 first  
**Gate:** Gate 2 of the approved Model Inspection worker integration  
**Scope:** Executable worker host, shared bounded stream transport, Windows process containment, low-level application-side worker client, deterministic abnormal-process fixture, and executable process-boundary evidence  

---

## 1. Executive summary

Gate 2 proves that Granite Edge AI can start, communicate with, cancel, time out, and clean up a protected Model Inspection worker without placing LLamaSharp, llama.cpp, or untrusted native work inside the WinUI process.

The boundary is:

```text
Future application service or probe
        |
        | project-owned worker request
        v
GraniteEdgeAI.ModelInspection.WorkerClient
        |
        | Windows-native process creation
        | bounded stdin / stdout / stderr
        v
GraniteEdgeAI.ModelInspection.Worker.exe
        |
        | IWorkerInspectionEngine
        v
UnavailableWorkerInspectionEngine in Gate 2
        |
        v
Controlled OperationalFailure
```

Unit tests substitute a scripted fake engine at `IWorkerInspectionEngine`. Real crash, hang, malformed-stream, environment-leak, handle-inheritance, cancellation, timeout, and process-tree scenarios are generated by a separate test-only executable. The production worker contains no hidden test modes.

Gate 2 does not inspect a real GGUF model. Its purpose is narrower and foundational: prove that the process boundary itself is deterministic, bounded, private, fail-closed, and able to contain abnormal worker behaviour before Gate 3 introduces LLamaSharp and native llama.cpp.

The key hardening decision is to create the worker with Windows `CreateProcessW` and `STARTUPINFOEX`, using both:

- `PROC_THREAD_ATTRIBUTE_JOB_LIST`, so the worker enters its Job Object as part of process creation rather than being assigned after it has started; and
- `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, so the child inherits only the three pipe handles it requires.

There is no fallback to an uncontained worker launch.

### 2.1 Preserved decisions

Gate 2 preserves:

- one short-lived worker per inspection;
- one versioned JSON object per UTF-8 line;
- redirected stdin, stdout, and stderr;
- no HTTP server, listener, TCP port, or required network access;
- model path sent through stdin, never process arguments;
- exact protocol, worker, runtime-profile, process-ID, and architecture identity;
- one hello, one start, monotonic progress, and one terminal result;
- cooperative cancellation first;
- forced termination represented as operational failure, never ordinary cancellation;
- x64 as the first production boundary;
- application classification kept outside the worker;
- no LLamaSharp dependency in the WinUI project or shared contracts.

### 2.2 Gate 2 refinements

This specification makes the following refinements explicit:

1. **A Windows Job Object is required in Gate 2.** It is no longer deferred hardening for this boundary.
2. **Job assignment must happen during process creation.** Starting a process and assigning it afterward is rejected because it creates a period in which the worker could execute outside the intended job.
3. **Inherited handles are allowlisted.** The worker receives only its stdin-read, stdout-write, and stderr-write handles.
4. **A separate transport project owns bounded stream framing.** The Gate 1 contracts project remains focused on immutable records, JSON rules, and protocol sequence rules.
5. **The child environment is constructed from a named allowlist.** The parent environment is not copied wholesale.
6. **The production Gate 2 engine is truthful.** It returns a stable engine-unavailable operational failure and never fabricates model evidence.
7. **Cleanup is proven at the complete Job Object level.** Waiting only for the root process is not sufficient evidence that descendants are gone.

### 2.3 Documentation consistency rule

Before Gate 2 can close, the umbrella specification, ADR-003, source READMEs, and evidence index must be updated where necessary so they no longer describe Job Object containment as deferred. Documentation must describe only behaviour that executable tests have proved.

## 3. Beginner glossary

### Worker process

A small separate program launched by the main application. If native model inspection crashes the worker, the WinUI application remains alive.

### Pipe

A one-way operating-system data channel. Gate 2 uses one pipe for commands into the worker and two pipes for worker output.

### Handle

A Windows reference to an operating-system resource such as a pipe, process, thread, or Job Object. Handles must be owned, restricted, and closed deliberately.

### Job Object

A Windows object that groups a process and its descendants. Gate 2 uses one unnamed Job Object per worker session so the complete worker process tree can be terminated and verified as empty.

### Handshake

The worker's first protocol message. It proves that the expected executable, protocol version, runtime profile, process, and architecture started.

### Fail closed

When identity, containment, framing, sequencing, or cleanup cannot be proved, the operation ends as an operational failure instead of continuing with weaker assumptions.

## 4. Goals

Gate 2 must:

1. create a plain .NET 8 x64 worker executable;
2. keep worker hosting independent from WinUI, XAML, and application outcome policy;
3. define an injectable `IWorkerInspectionEngine` seam;
4. compose a truthful unavailable engine in the production Gate 2 worker;
5. share one strict byte-bounded line transport between worker and client;
6. resolve the worker only from an approved absolute root;
7. create a dedicated Job Object before process creation;
8. set `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and allow no breakaway policy;
9. assign the worker to the Job Object through `PROC_THREAD_ATTRIBUTE_JOB_LIST` during `CreateProcessW`;
10. inherit only three explicit pipe handles through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`;
11. construct a minimal, reviewed Unicode environment block;
12. disable .NET diagnostic ports for the worker boundary;
13. drain stdout and stderr concurrently without deadlock;
14. retain at most 256 KiB of redacted stderr while continuing to drain all remaining bytes;
15. enforce the existing one-MiB UTF-8 protocol-line limit before unbounded buffering;
16. reject malformed UTF-8, BOM-prefixed payloads, duplicate JSON properties, invalid ordering, wrong IDs, and unknown message kinds;
17. enforce the five-second startup timeout, five-minute overall timeout, and five-second cancellation grace separately;
18. distinguish cooperative cancellation from forced cleanup;
19. cross-check terminal message, process exit code, forced-termination state, and request ID;
20. terminate and verify the complete worker process tree after crash, hang, timeout, cancellation failure, or disposal;
21. prevent path, environment, secret, model-byte, chat-template, raw-protocol, and unrestricted-stderr leakage;
22. provide deterministic unit and real-process tests for normal and abnormal behaviour;
23. preserve all Gate 1 tests and dependency rules;
24. produce inspectable CI and evidence artifacts before the gate is described as complete.

- long-lived worker reuse or multiple requests per process.

These exclusions are deliberate gate boundaries, not omissions.

## 6. Alternatives and trade-offs

### 6.1 `System.Diagnostics.Process` followed by `AssignProcessToJobObject`

**Rejected as the production launch path.** It is easy to write, but the process starts before job assignment. It also makes precise handle inheritance harder to demonstrate. Gate 2 requires containment and handle policy to be properties of process creation itself.

`System.Diagnostics.Process` may still be used in tests for observing unrelated helper processes, but not as the production worker launcher.

### 6.2 `CreateProcessW` with `CREATE_SUSPENDED`, followed by assignment, then resume

**Not selected.** It can reduce the launch race, but `PROC_THREAD_ATTRIBUTE_JOB_LIST` provides direct creation-time assignment on the supported Windows baseline and avoids a separate suspended-thread state and resume failure path.

### 6.3 `CreateProcessW` with `STARTUPINFOEX`, job list, and handle list

**Selected.** It gives the launcher explicit control over executable identity, environment, working directory, creation flags, Job Object membership, standard-stream handles, and handle inheritance.

### 6.4 Restricted token or AppContainer

**Deferred after explicit trade-off analysis.** These mechanisms can reduce authority further, but they add token creation, capability, ACL, package, model-file-access, native-library, and support complexity. The current Gate 2 threat model primarily addresses accidental native failure, malformed protocol output, process hangs, and resource leakage. A sandbox evaluation remains a later security-hardening task and must not be claimed by Gate 2.

### 6.5 Named pipes or local HTTP

**Rejected for protocol version 1.** Redirected anonymous pipes are sufficient for one short-lived local request. HTTP would add a listener, endpoint lifecycle, port conflicts, and a wider attack surface. Named pipes remain replaceable behind the client boundary if a later long-lived service creates a demonstrated need.

### 6.6 Put stream framing in the contracts project

**Rejected.** Immutable protocol records and JSON validation are contracts. Stream reading, line termination, buffering, and cancellation are transport mechanics. A small separate transport project keeps both responsibilities cohesive while allowing worker and client to share one implementation.

### 6.7 Duplicate framing code in worker and client

**Rejected.** Independent implementations can disagree at exactly the trust boundary where consistency matters. One shared pure transport library is smaller and easier to verify.

### 7.1 Dependency direction

Allowed:

```text
Transport -> Contracts
Worker -> Contracts + Transport
WorkerClient -> Contracts + Transport
Unit/integration tests -> the production project under test
Process fixture -> Contracts + Transport only where a valid protocol scenario needs them
```

Forbidden:

```text
Contracts -> Transport, Worker, WorkerClient, WinUI, LLamaSharp
Transport -> Worker, WorkerClient, WinUI, LLamaSharp
Worker -> WorkerClient, WinUI, LLamaSharp in Gate 2
WorkerClient -> Worker implementation, WinUI, LLamaSharp
Production projects -> process fixture or test projects
WinUI application -> worker executable implementation project
```

### 7.2 Project configuration

- Contracts and Transport remain pure `net8.0` libraries.
- Worker and WorkerClient explicitly target Windows and the supported Windows 10/11 desktop baseline.
- Worker and all real-process tests target x64 with `win-x64` where a runtime identifier is needed.
- New projects enable nullable reference types, .NET analyzers, deterministic builds, and warnings-as-errors.
- Unsafe code is disabled by default. Any unavoidable unsafe interop must remain in one reviewed file and be justified by a test-backed comment.
- Production projects do not enable trimming until Gate 4 proves reflection, serialization, and native interop compatibility in published output.

### 7.3 Why the client is a separate infrastructure project

Real crash and hang tests must execute outside the WinUI/XAML test host. A pure infrastructure library also gives later gates one replaceable adapter boundary. Gate 5 can map application requests into this low-level worker client without moving Windows process code into a page, ViewModel, or service.

## 9. Process creation trust boundary

### 9.1 Trusted executable resolution

The production resolver must:

1. receive an approved build/install root from controlled application composition, not from model data or arbitrary user input;
2. reject an empty or relative root;
3. combine that root with the fixed worker relative path;
4. use `Path.GetFullPath` on both root and candidate;
5. normalise extended-length (`\\?\`) and volume-path forms before Windows case-insensitive, separator-qualified comparison;
6. reject a candidate equal to the root directory itself;
7. reject missing files, directories, and unsupported architecture using a PE/x64 preflight check;
8. inspect every existing root-to-file segment for unexpected reparse points;
9. resolve both root and executable final paths through maintained file handles and verify that the executable remains beneath the approved final root;
10. perform verification immediately before launch and keep the executable verification handle alive through process creation where the API permits;
11. never search `PATH`, the current directory, the model directory, Downloads, or another user-writable fallback location;
12. never accept a user-selected worker executable.

Gate 2 does not claim complete time-of-check/time-of-use protection or package authenticity. Gate 4 must add immutable package-root, exact closure, hash/signature, publish, and MSIX evidence.

### 9.2 Absolute application name

`CreateProcessW` receives the verified absolute worker path through `lpApplicationName`. It is never null. This avoids executable-name ambiguity and path search.

The writable command-line buffer contains only the quoted worker executable path required for conventional `argv[0]`. It contains no model path, request ID, test scenario, environment secret, or diagnostic text.

### 9.3 Controlled working directory

The production worker working directory is an approved application-owned worker directory. It is not inherited from the parent, set to the model directory, or selected by the user.

The worker must not use the working directory to discover alternate binaries or model files.

## 10. Atomic Job Object containment

### 10.1 Job creation

Before any worker process exists, the launcher creates one unnamed Job Object and configures:

```text
JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE
```

Neither `JOB_OBJECT_LIMIT_BREAKAWAY_OK` nor `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` is set.

The Job Object handle is not inheritable and is not included in the child handle list.

### 10.2 Creation-time assignment

The launcher creates a two-entry `PROC_THREAD_ATTRIBUTE_LIST` containing:

```text
PROC_THREAD_ATTRIBUTE_JOB_LIST
PROC_THREAD_ATTRIBUTE_HANDLE_LIST
```

The job-list entry contains the session's Job Object handle. The handle-list entry contains only:

```text
child stdin read handle
child stdout write handle
child stderr write handle
```

`CreateProcessW` uses:

```text
EXTENDED_STARTUPINFO_PRESENT
CREATE_NO_WINDOW
CREATE_UNICODE_ENVIRONMENT
```

and `bInheritHandles = TRUE`, because the explicit handle list requires inheritance to be enabled.

No `CREATE_BREAKAWAY_FROM_JOB` flag is used.

If attribute-list creation, Job Object configuration, pipe construction, environment construction, or `CreateProcessW` fails, no weaker launch is attempted. The client reports a stable operational failure and closes all partially created resources.

### 10.3 Why `CREATE_SUSPENDED` is not required

The selected job-list attribute assigns the new process during creation on the supported Windows baseline. Adding a suspended-state/resume path would create extra failure states without strengthening the selected guarantee. This decision must be revisited only if executable evidence contradicts the documented Windows behaviour.

### 10.4 Nested-job behaviour

The launcher must work when the main application itself already runs in a Windows job, provided Windows nested-job rules permit the additional job. A failure caused by incompatible parent-job policy is an operational launch failure. The client must not silently continue without its own Job Object.

### 10.5 Complete-tree cleanup

Normal completion waits for the root process and verifies the Job Object's active process count becomes zero. If the root exits but another associated process remains beyond the normal cleanup deadline, the client records a process-tree integrity failure and terminates the job.

Forced cleanup uses:

1. `TerminateJobObject` with a stable forced-termination exit code;
2. bounded waiting for the root process handle;
3. `QueryInformationJobObject` to confirm no active associated process remains;
4. closing the final Job Object handle as the last kill-on-close safeguard.

Root-process exit alone is not accepted as complete-tree cleanup evidence.

### 10.6 Job Object resource limits

Gate 2 requires process-tree containment but does not set speculative CPU, working-set, commit-memory, or wall-clock Job Object limits. The protocol timeouts remain the controlling time policy. Gate 3 must measure LLamaSharp behaviour before resource limits are added.

The production worker is expected to create no child process. An active-process limit may be added only after a focused compatibility test proves it does not interfere with the .NET host or Gate 3 runtime. The absence of that limit does not weaken no-breakaway process-tree containment.

## 11. Exact handle inheritance

### 11.1 Pipe directions

```text
Parent writes -> worker stdin
Worker writes -> parent stdout
Worker writes -> parent stderr
```

Each anonymous pipe is created with an inheritable child end and a non-inheritable parent end.

### 11.2 Handle allowlist

`PROC_THREAD_ATTRIBUTE_HANDLE_LIST` contains exactly three valid inheritable handles. It contains no:

- parent pipe end;
- process or thread handle;
- Job Object handle;
- file handle;
- token;
- socket;
- event;
- registry key;
- pseudo handle;
- unrelated inheritable handle from the application.

`STARTF_USESTDHANDLES` is set, and the three `STARTUPINFO` standard-handle fields match the same allowlist.

### 11.3 Post-launch closure

Immediately after successful creation, the parent closes its copies of all child pipe ends and the primary thread handle. The session retains only:

- parent stdin-write stream;
- parent stdout-read stream;
- parent stderr-read stream;
- process handle;
- Job Object handle;
- cancellation/timeout resources;
- stream tasks and bounded diagnostic state.

### 11.4 Handle-leak tests

The process fixture includes an inherited-handle probe. The test starts with additional deliberately inheritable parent handles and proves the child cannot access them. It also proves the three required standard handles are valid.

## 12. Child environment policy

### 12.1 Empty-by-default construction

The launcher does not clone the complete parent environment. It builds a new Unicode environment block from a named, versioned allowlist.

The Gate 2 baseline copies only these reviewed operating-system/runtime values when present and validated:

```text
SystemRoot
WINDIR
TEMP
TMP
DOTNET_ROOT          when present and validated
DOTNET_ROOT_X64      when present and validated
```

The launcher then adds these fixed security values explicitly; they are part of the final allowlisted block rather than copied from the parent:

```text
DOTNET_EnableDiagnostics=0
DOTNET_EnableDiagnostics_IPC=0
DOTNET_EnableDiagnostics_Debugger=0
DOTNET_EnableDiagnostics_Profiler=0
```

No caller may append arbitrary environment variables through the public production client.

### 12.2 Validation rules

- variable names are compared case-insensitively;
- duplicate names differing only by case are rejected;
- names containing `=` or NUL are rejected;
- values containing NUL are rejected;
- `TEMP` and `TMP` are absolute existing paths selected by the launcher and contain no model-derived component;
- conditional .NET roots are absolute, existing, and not taken from user/model input;
- the block is sorted case-insensitively as required by Windows conventions;
- each entry is NUL-terminated and the complete block is double-NUL-terminated;
- `CREATE_UNICODE_ENVIRONMENT` is mandatory.

### 12.3 Variables that must not leak

Tests seed and then prove absence of representative:

```text
PATH
PATHEXT
GITHUB_*
ACTIONS_*
NUGET_*
AZURE_*
AWS_*
OPENAI_*
IBM_*
HF_*
HUGGINGFACE_*
TOKEN
SECRET
PASSWORD
DOTNET_DiagnosticPorts
DOTNET_EventPipeOutputPath
COMPlus_*
project-specific model or evidence variables
```

The deny examples do not replace the allowlist. A variable absent from the allowlist is excluded even when its name is not listed above.

### 12.4 Evidence-driven adjustment

If the framework-dependent Gate 2 worker cannot start with the baseline allowlist, the allowlist may change only through:

1. a failing executable test that demonstrates the missing requirement;
2. a documented explanation of why the variable is required;
3. a privacy/security review;
4. a focused allowlist test;
5. a specification and README update.

The complete parent environment is never an acceptable fallback.

## 13. Shared bounded transport

### 13.1 Encoding

Both sides use one shared strict encoding instance equivalent to:

```text
UTF-8
no byte-order mark
throw on invalid bytes
```

A UTF-8 BOM at the beginning of a protocol line is rejected rather than silently accepted.

### 13.2 Framing

One compact JSON object is followed by one line-feed byte (`0x0A`). The writer does not emit a carriage return. The reader may reject carriage-return framing instead of normalising it; both production sides always emit LF-only frames.

Newlines inside JSON strings are escaped by JSON serialization and therefore do not terminate a frame.

### 13.3 Byte-based limit

The maximum command or message line remains exactly one MiB of UTF-8 bytes, excluding the terminating LF.

The reader counts bytes while reading and stops immediately when the limit is exceeded. It does not first construct an unbounded string and measure it afterward.

The writer serializes through the existing strict `WorkerProtocolJson`, checks the byte count, appends one LF, writes the complete frame, and flushes before awaiting a response that depends on that frame.

### 13.4 EOF rules

```text
EOF with no buffered byte
    -> clean stream end

EOF after a complete terminal exchange
    -> expected shutdown

EOF with a non-empty unterminated frame
    -> protocol failure

EOF before hello, before started, or before terminal
    -> operational process failure at the client

stdin EOF in the worker before normal terminal completion
    -> cooperative cancellation request and parent-loss handling
```

### 13.5 Reader/writer cancellation

Every read, write, and flush accepts a cancellation token. Cancellation does not convert malformed or oversized data into an ordinary cancellation result. The first proven failure category is preserved.

### 13.6 Single-writer ordering and bounded queues

Neither side permits concurrent callers to write bytes directly to one protocol stream. Commands pass through one client writer, and worker messages pass through one worker output coordinator. Progress callbacks cannot interleave bytes with a terminal frame.

Any internal message queue is bounded and has a named capacity. Queue overflow or a progress consumer that cannot keep up becomes a controlled operational failure; it never causes unbounded memory growth. The implementation may coalesce equivalent progress updates but may not reorder or invent progress.

### 13.7 JSON validation

After framing, the existing Gate 1 JSON implementation remains authoritative:

- exact protocol version;
- exact case-sensitive discriminators;
- string enums only;
- duplicate-property rejection at every object depth;
- bounded JSON depth;
- no comments or trailing commas;
- no trailing data after the JSON object;
- unknown additive fields tolerated within protocol version 1;
- record validation before serialization and after deserialization.

## 14. Standard output and standard error

### 14.1 Stdout

Stdout is protocol-only. The first stdout frame must be hello. Any prefix, banner, logging line, blank frame, BOM, or diagnostic text before hello is a protocol failure.

Production code must never write ordinary console logging to stdout.

### 14.2 Stderr

Stderr is diagnostic-only and never parsed as protocol.

The client starts stderr draining immediately after successful process creation and continues draining raw bytes until EOF, even after retained storage reaches 256 KiB. Decoding happens only on the bounded retained prefix so an invalid sequence cannot stop pipe drainage and deadlock the worker.

Retention rules:

- maximum retained UTF-8 content: 256 KiB;
- invalid UTF-8 sets a safe `InvalidUtf8` diagnostic flag and discards undecodable retained text rather than leaking raw bytes;
- sensitive text is redacted before retention;
- a `WasTruncated` flag records discarded content;
- discarded bytes are still consumed;
- no raw model path, model bytes, full chat template, prompt, environment block, secret, or raw protocol frame is retained;
- retained stderr is infrastructure diagnostic evidence and is not directly displayed by a page or returned as model evidence.

### 14.3 Deadlock prevention

Stdout reading, stderr draining, process-exit waiting, and stdin command writing are independent asynchronous operations. The client never waits synchronously for process exit while either output pipe may still fill.

Normal and abnormal shutdown await or safely dispose all stream tasks under a bounded cleanup deadline.

## 15. Production worker host

### 15.1 Engine seam

```csharp
IWorkerInspectionEngine
    -> ExecuteAsync(validatedStartCommand, progress, cancellationToken)
    -> WorkerEngineResult
```

The interface and result contain worker-protocol concepts only. They contain no page, XAML, ViewModel, application classification, LLamaSharp, or native handle type.

### 15.2 Gate 2 production composition

`Program` composes:

```text
WorkerHost
    + UnavailableWorkerInspectionEngine
    + real bounded stdin/stdout/stderr
    + real parent monitor
```

After a valid start, the unavailable engine returns one controlled `OperationalFailure` terminal result with stable code:

```text
MI-OP-ENGINE-NOT-CONFIGURED
```

The user-safe message states that the inspection runtime is not yet installed in this gate. It does not blame the model and does not expose a path.

The unavailable engine must not open, hash, modify, map, or inspect the model file. Gate 2 therefore proves process mechanics without making a false model-inspection claim.

### 15.3 Unit-test composition

Worker unit tests inject a scripted fake engine that can:

- emit deterministic progress;
- return completed evidence built from safe test data;
- return controlled operational failure;
- observe cancellation;
- throw a managed exception;
- block on a synchronization primitive.

This fake exists only in the test project. The production worker project contains no scenario switch, crash command, hang command, or malformed-output option.

## 16. Worker lifecycle state machine

```text
Boot
  -> HelloSent
  -> AwaitingStart
  -> Running
  -> CancellationRequested       optional
  -> TerminalSent
  -> Exited
```

`Failed` may be entered from any non-terminal state, but no message may follow a terminal message.

Rules:

1. hello is emitted exactly once and before reading a start command;
2. one valid start command is accepted;
3. started is emitted exactly once before engine progress;
4. zero or more matching cancel commands are idempotent while running;
5. a second start, wrong request ID, command after terminal, malformed command, or invalid transition is a protocol failure;
6. command reading continues while the engine runs so cancellation can be received;
7. engine completion, parent loss, stdin EOF, protocol failure, and cancellation race through one terminal coordinator;
8. the terminal coordinator can win exactly once;
9. the engine is given a linked cancellation token;
10. the worker disposes engine resources through `finally` when Gate 3 adds them;
11. all stdout messages pass through one serialized output coordinator;
12. stdout is flushed after hello, started, progress, and terminal frames;
13. a protocol violation cancels the engine, writes only a safe stderr diagnostic, and exits with code 2 without pretending that a normal terminal result was produced;
14. stderr diagnostics are bounded and redacted.

## 17. Parent-loss monitoring

The start command carries:

- parent process ID;
- parent process creation time in UTC, captured from the native process handle at Windows `FILETIME` precision.

The worker opens the parent once with the minimum query/synchronisation access, compares the native creation time, and then keeps that verified handle open while waiting asynchronously for parent exit. This avoids repeated PID lookup and prevents a recycled PID from being mistaken for the original parent.

Parent-loss signals are:

1. stdin EOF before normal terminal completion;
2. the verified parent process handle becomes signalled;
3. the initial PID/creation-time validation fails.

Any signal requests cooperative cancellation. The worker still attempts one controlled terminal result when stdout remains usable.

The Job Object is the hard cleanup mechanism when the parent disappears and its final job handle closes. The maintained parent handle and stdin EOF are secondary cooperative mechanisms that allow orderly engine disposal and a truthful terminal message when possible.

The parent wait is cancellation-aware and uses the maintained waitable handle. It does not busy-spin or repeatedly reopen the PID.

## 18. Client lifecycle state machine

```text
NotStarted
  -> ResolvingExecutable
  -> CreatingBoundary
  -> AwaitingHello
  -> Ready
  -> StartSent
  -> Running
  -> CancellationRequested       optional
  -> TerminalReceived
  -> AwaitingExit
  -> VerifyingJobEmpty
  -> Completed
  -> Disposed
```

A `Failed` transition may occur from every non-terminal state. Failure and disposal are idempotent.

### 18.1 Session ownership

One `WorkerProcessSession` owns:

- process handle and PID;
- primary thread handle until closed immediately after launch;
- Job Object handle;
- parent stream ends;
- stdout reader task;
- stderr drainer task;
- process-exit waiter;
- timeout and linked cancellation sources;
- lifecycle state;
- retained safe diagnostics;
- forced-termination flag;
- terminal/exit integrity result.

No handle or stream is owned by two independent disposers.

### 18.2 `SafeHandle` requirement

Native process, thread, job, pipe, and attribute-list resources use framework-provided safe handles where available, including `Microsoft.Win32.SafeHandles.SafeProcessHandle`, and narrow custom `SafeHandle` types where Windows provides no suitable public type. Raw `IntPtr` values may exist only inside the interop layer and must not escape into business or protocol types.

The primary cleanup path remains explicit `DisposeAsync`/`finally`; finalization is a last-resort leak safeguard, not normal lifecycle control.

### 18.3 Interop correctness rules

- prefer source-generated `LibraryImport` declarations with explicit UTF-16 marshalling and `SetLastError=true`;
- use x64-correct pointer-sized fields for `SIZE_T`, `ULONG_PTR`, handles, and attribute values;
- set every structure size field explicitly and test it against the x64 ABI;
- capture `GetLastError` immediately after a failed native call, before any cleanup call can overwrite it;
- free attribute lists and unmanaged environment buffers in `finally`, zeroing buffers that could contain environment values;
- close the primary thread handle immediately after successful creation;
- wait using the maintained native process handle rather than resolving a process only by PID.

### 18.4 Public API and concurrency semantics

The production client exposes one high-level asynchronous run operation. Expected launch, protocol, worker, timeout, and cleanup failures return a typed `WorkerClientResult`; they do not escape as raw `Win32Exception` or JSON exceptions. Programmer misuse may throw argument/state exceptions. Cancellation before a verified request becomes active may surface `OperationCanceledException`; cancellation after start follows the verified cooperative/forced rules in this specification.

Progress is delivered sequentially through an asynchronous callback or equivalent bounded abstraction. A caller callback failure becomes a caller-side operational failure and triggers safe worker cleanup. Raw stream readers never invoke UI code directly.

The client has no global mutable session. Separate calls own separate streams and Job Objects and may run concurrently without mixing request IDs, progress, diagnostics, or cleanup. A focused concurrent-session integration test is required.

The client verifies:

- worker ID exactly `GraniteEdgeAI.ModelInspection.Worker`;
- worker version accepted by the Gate 2 exact-version policy;

- process architecture exactly x64;

- no duplicate hello follows;
- the process has not already exited;
- the process remains associated with the expected Job Object.

The subsequent `MI-OP-ENGINE-NOT-CONFIGURED` terminal result is authoritative. ## 20. Start, progress, terminal, and exit integrity

### 20.1 Start

Only after a valid hello does the client send one `WorkerStartInspectionCommand` through stdin.

The model path exists only inside that bounded JSON command. It is absent from:

- process command line;
- working directory;
- environment;
- worker hello;
- diagnostic messages;
- client exception text;
- retained stderr;
- CI command echo.

### 20.2 Progress

The client establishes the expected request ID before validating request-scoped messages. Started and progress messages must match it.

Progress must follow the Gate 1 sequence validator and remain monotonic. A backward value, duplicate started, progress before started, progress after terminal, or wrong request ID is a protocol failure.

### 20.3 Terminal result

Exactly one completed frame is required for a normal protocol completion. It may contain:

- `Completed` with evidence;
- `Cancelled` with no evidence or failure;
- `OperationalFailure` with one controlled failure and no evidence.

The client does not treat a terminal frame as final proof until process exit and Job Object cleanup are also verified.

### 20.4 Stable exit codes

```text
0 -> terminal Completed with reliable evidence
1 -> terminal OperationalFailure
2 -> protocol failure
3 -> terminal cooperative Cancelled
```

Launch failures occur before worker protocol and are represented by client-side stable failure codes rather than a worker exit code.

### 20.5 Cross-check table

```text
Completed terminal + exit 0 + no forced kill + empty job
    -> valid completed worker result

OperationalFailure terminal + exit 1 + no forced kill + empty job
    -> valid controlled worker failure

Cancelled terminal + exit 3 + cancellation requested + no forced kill + empty job
    -> valid cooperative cancellation

Protocol failure exit 2
    -> operational protocol failure, never a model result

Any terminal + inconsistent exit code
    -> operational integrity failure

Success exit without terminal
    -> operational integrity failure

Terminal followed by another protocol frame
    -> operational protocol failure

Crash or pipe loss without terminal
    -> operational process failure

Any forced Job Object termination
    -> operational forced-termination failure
```

Partial progress and partial evidence are discarded after any integrity failure.

## 21. Timeout and cancellation policy

Three independent clocks are required:

```text
Startup handshake timeout:       5 seconds
Overall inspection timeout:      5 minutes
Cooperative cancellation grace:  5 seconds
```

They are named contract values from Gate 1 and are not replaced by arbitrary sleeps. Unit tests inject .NET `TimeProvider` (or an equivalent clock seam); real process tests use wall-clock deadlines only where operating-system behaviour must be exercised.

### 21.1 User cancellation

When the caller's cancellation token is signalled after start:

1. the client writes at most one matching cancel command;
2. it flushes stdin;
3. it starts the five-second grace clock;
4. it continues reading stdout and stderr;
5. a valid Cancelled terminal plus exit 3 within grace is returned as cooperative cancellation;
6. any other terminal/exit combination is validated normally;
7. grace expiry forces Job Object termination and returns operational failure.

Cancellation before successful start cancels launch/handshake work and cleans the Job Object. It cannot yield a worker `Cancelled` result because no verified request existed.

### 21.2 Overall timeout

Overall timeout requests cancellation through the same cooperative path, but the resulting client failure retains a timeout-specific stable code. A cooperative worker Cancelled terminal does not erase that the trigger was the overall safety timeout.

### 21.3 Forced cleanup

Forced cleanup occurs for:

- startup timeout;
- overall timeout followed by grace expiry;
- ignored cancellation;
- protocol corruption;
- duplicate/post-terminal output;
- client disposal while active;
- root hang;
- incomplete process-tree exit;
- stream task that cannot finish within cleanup deadline.

Forced cleanup is never reported as ordinary cancellation, even if a cancel command was sent first.

## 28. Risks and explicit deferrals

### 28.1 P/Invoke complexity

The Windows launcher uses low-level APIs and therefore has memory-layout, lifetime, and error-handling risk. Mitigations are a narrow internal interop layer, `SafeHandle` ownership, structure-size tests, real-process tests, code review, and no use of native values outside the launcher.

### 28.2 Framework-dependent worker startup

A minimal environment may expose an undocumented deployment assumption. The allowlist-adjustment rule requires evidence rather than falling back to the complete parent environment. Gate 4 will provide the final packaged runtime closure.

### 28.3 Parent job policy

Some hosting environments may impose job limits that conflict with nested containment. This must fail clearly and be evidenced. The production client does not drop containment to accommodate such an environment.

### 28.4 Filesystem replacement race

Final-path validation reduces path confusion but does not prove immutable executable content between check and launch. Gate 4 owns package-root immutability, hash/signature, exact closure, and installer evidence.

### 28.5 Process mitigation policy

Additional `PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY` options are deferred until tested against the .NET runtime and Gate 3 LLamaSharp/native DLL loading. Policies that break the runtime are not security improvements. The deferral and compatibility test must be revisited before production release.

### 28.6 Restricted token or AppContainer

Deferred for a dedicated threat-model and file-access spike. Gate 2 is a crash/resource/protocol containment boundary, not a privilege sandbox.

### 28.7 Job resource limits

CPU, memory, and active-process limits are deferred until Gate 3 provides representative runtime measurements. Process-tree containment and timeouts are mandatory now.

### 28.8 Completion-port notifications

A Job Object completion port may improve observability, but notification delivery alone is not used as a correctness guarantee. Gate 2 uses maintained handles and `QueryInformationJobObject` for final cleanup proof. A completion port may be added later without changing the public client contract.

## 31. Official Microsoft technical basis

The implementation plan must verify details against the current official Microsoft documentation before coding:

- **Create processes - Win32 apps**: explicit handle-inheritance warning, `STARTUPINFOEX`, writable command line, and handle closure.
- **UpdateProcThreadAttribute**: `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` and `PROC_THREAD_ATTRIBUTE_JOB_LIST` requirements.
- **InitializeProcThreadAttributeList** and **STARTUPINFOEX**: allocation, initialization, destruction, and `EXTENDED_STARTUPINFO_PRESENT`.
- **CreateProcessW**: absolute application name, Unicode environment, standard handles, creation flags, and result handles.
- **Job Objects**, **CreateJobObjectW**, **SetInformationJobObject**, **TerminateJobObject**, and **QueryInformationJobObject**: process-tree membership, no-breakaway policy, kill-on-close, termination, and active-process verification.
- **UTF8Encoding**: no BOM and invalid-byte exceptions.
- **Process redirected-stream guidance**: concurrent asynchronous output draining to avoid deadlock.
- **.NET diagnostic port** and **.NET environment variables**: sensitive diagnostic access and `DOTNET_EnableDiagnostics=0`.
