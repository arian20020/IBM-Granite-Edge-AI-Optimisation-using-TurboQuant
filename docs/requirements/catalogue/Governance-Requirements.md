# Governance and Project-Control Requirements

**Baseline:** MoSCoW v1.2 / RTM v1.3  
**Owner:** Arian B  
**Presentation change:** CHG-014 / CR-014 — no scope change  

> The controlled workbook and full RTM contain rationale, mappings, acceptance criteria, verification methods and evidence paths.

| ID | Priority | Release Role | Lifecycle | Requirement |
|---|---|---|---|---|
| G-M01 | Must | Core | Active | The project problem, aim, research questions, objectives, first-release scope, exclusions and satisfactory outcome must be version-controlled. |
| G-M02 | Must | Core | Active | The project must maintain one versioned MoSCoW requirements baseline with stable IDs and measurable acceptance criteria. |
| G-M03 | Must | Core | Active | The project must maintain bidirectional traceability from requirements to objectives/RQs, work packages, implementation, tests and evidence. |
| G-M04 | Must | Core | Active | The project must record proportionate architecture views, key ADRs, stable contracts, states and diagnostic codes. |
| G-M05 | Must | Core | Active | The project must maintain a consolidated risk, assumption, constraint and licence register. |
| G-M06 | Must | Core | Active | Requirement and scope changes must be linked to dated decisions, GitHub issues, pull requests/commits and affected tests. |
| G-M07 | Must | Core | Active | Irreplaceable raw evidence from completed feasibility campaigns must be recovered, hashed, indexed and backed up. |
| G-M08 | Must | Core | Active | The release must include a README, user manual, developer/build guide, known limitations and final feature-status table. |
| G-M09 | Must | Core | Active | The final release must be tied to a Git tag, checksums, evidence pack, independent backup and evidence-based answers to every RQ. |

Do not edit this category file independently of the controlled RTM workbook.
