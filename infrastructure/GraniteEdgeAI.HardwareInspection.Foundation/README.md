# Hardware Inspection Foundation

This project contains candidate-neutral Windows foundations for Hardware Inspection. Gate 7 now composes these foundations behind the x64 product service, while acquisition, collection, resolution, outcomes, and lifecycle policy remain application-owned boundaries.

## Boundaries

- `WindowsSystemSnapshotProvider` captures physically installed, OS-usable, and currently available memory as distinct byte values, plus a UTC capture time and bounded OS facts.
- `TrustedToolPackageVerifier` accepts only an exact flat manifest under an approved root. It rejects path escape, reparse points, inventory drift, hash mismatch, and non-AMD64 PE images.
- Verification retains no-follow directory and member handles with deny-write/delete sharing. Hashing uses the retained executable handle, closing the path-inspection/open race.
- `VerifiedTrustedTool` is `IDisposable`. Callers must retain it for every execution and dispose it when the approved package is no longer needed. Execution takes a reference-counted custody lease, so concurrent owner disposal cannot release package custody early.
- `ExternalProcessRunner` accepts only a manifest-declared command identity. It has no shell or arbitrary command-string API.
- The runner creates the process suspended, restricts inherited handles to three standard-stream pipes, assigns and verifies the process in a private kill-on-close Windows Job Object, then resumes it. Timeout, cancellation, output limits, and normal parent exit all perform bounded descendant cleanup.
- `LlmFitHardwareEvidenceProvider` accepts only a live verified `llmfit` v1.1.9 package whose manifest contains exactly `version --version` and `system --no-dashboard --json system`. It does not accept caller-supplied arguments or dispose caller-owned custody.
- `LlamaCppCapabilityEvidenceProvider` accepts only a live verified `granite-edge-hardware-llamacpp-probe` `0.27.0-cpu-win-x64` package with exactly the `identity` and `capabilities` JSON-v1 commands. Identity runs before capability capture; each phase has independent time and output bounds, and every process remains under `ExternalProcessRunner` custody.
- Llama.cpp identity is pinned to LLamaSharp/CPU backend `0.27.0`, LLamaSharp commit `7cbbc45e421d55794d5050d126e0b96511007007`, mapped llama.cpp commit `3f7c29d318e317b63f54c558bc69803963d7d88c`, and `win-x64`. Available evidence requires exactly backend `cpu` and 1..16 contiguous devices with bounded safe buffer-type labels; output, native logs, paths, and model data are not retained.
- The native LLamaSharp runtime is isolated in `GraniteEdgeAI.HardwareInspection.LlamaCppProbe.exe`. The app and Foundation assemblies contain no LLamaSharp/native package reference. Gate 7 verifies the packaged probe against its detached exact-inventory SHA-256 manifest before the bounded external runner may launch it; native runtime code is never loaded into the app process.
- Each capture checks the exact `llmfit 1.1.9` version output with a 5-second timeout and independent 4 KiB stream limits, then invokes system inspection once with a 15-second timeout and independent 256 KiB stream limits. There is no retry, fallback, shell, PATH search, dashboard, listener, or network operation.
- System JSON parsing uses `System.Text.Json` with comments and trailing commas disabled and maximum depth 16. Unknown properties are tolerated, while duplicate properties, case drift, unsafe names, invalid CPU/RAM ranges, and contradictory GPU shapes fail closed through the bounded `LlmFitDiagnosticCode` enum.
- Provider evidence is immutable and noncanonical. It retains validated source GiB values, bounded CPU/GPU names, UTC capture time, and a lowercase SHA-256 of bounded system stdout; it never retains raw stdout, stderr, exit messages, paths, or exception text. The x64 application-side Gate 6 resolver now owns Windows authority, checked unit normalization, closed freshness/tolerance policy, cross-provider consistency, provenance, and canonical snapshot construction without changing this Foundation boundary.
- `HardwareText` validates names and OS facts by Unicode scalar value, caps them at 256 scalars, rejects invalid UTF-16, boundary whitespace, controls, format/bidirectional controls, and line/paragraph separators, and neither normalizes nor truncates accepted text.
- `WindowsProcessorEvidenceProvider` reads only the bounded hardware-description processor name, maps native architecture from `GetNativeSystemInfo`, counts physical-core records from a maximum 1 MiB `GetLogicalProcessorInformationEx(RelationProcessorCore)` buffer, and obtains the all-group active logical count from `GetActiveProcessorCount(ALL_PROCESSOR_GROUPS)`. Every core record must contain exactly one group affinity; counts remain in `1..4096` with physical cores no greater than logical processors.
- `WindowsStorageEvidenceProvider` obtains the Windows system directory into a fixed 32,768-character buffer, derives its volume root only inside the native adapter, and calls `GetDiskFreeSpaceExW`. Evidence exposes only positive total capacity and bytes available to the caller, with `available <= capacity`; no path is retained.
- `DxgiGraphicsEvidenceProvider` uses only DXGI 1.1 `CreateDXGIFactory1`, `IDXGIFactory1.EnumAdapters1`, and `IDXGIAdapter1.GetDesc1`. Enumeration retains at most 64 adapters, treats `DXGI_ERROR_NOT_FOUND` as the sole successful terminator, releases every acquired COM object, and preserves dedicated-video, dedicated-system, and shared-system memory as three independent values. Zero adapters is available/absent evidence; factory, enumeration, description, and limit failures are unavailable evidence.
- `UnavailableNeuralProcessorProbe` is the production-safe provisional NPU boundary. It honors cancellation and returns `DetectionUnavailable(EnumerationMechanismNotApproved)`; it never reports `NotPresent` or infers an NPU from CPU, GPU, registry, runtime, or model data.
- Windows processor, memory/OS, storage, DXGI, LLM Fit, and NPU outputs remain separate provider evidence. This project does not compare them, select a primary adapter, identify Intel hardware, calculate usable graphics memory, or construct the app-domain `HardwareSnapshot`.

## Deliberate non-features

The foundation contains no model data, GGUF/OpenVINO interpretation, compatibility calculation, provider-resolution policy, product coordinator, candidate download, network access, or production LLM Fit package. LLM Fit v1.1.9 remains an unsigned Gate 1 candidate with `FunctionalPassWithPackagingConcern`; redistribution remains blocked pending an approved signed/package provenance and transitive-license closure.

Gate 3 supplies the infrastructure-only LLM Fit command/parser/evidence adapter behind this boundary. Gate 4 adds bounded Windows processor, memory/OS, system-volume, DXGI graphics, and provisional NPU evidence without activating product composition. Gate 5 adds pinned llama.cpp identity, backend, visible-device evidence, an isolated native child probe, and deterministic inactive packaging without loading native runtime code into the app or test host. Its development acceptance is complete at `a9c27a59e487336a4a6b79099d35948015c34a4c`: three normally installed, registered-AUMID repetitions in a disposable guest each passed 32/32 with package identity and a developer signature. The hash-bound self-signed route exports no private key, records both `publicTrustVerified` and `smartAppControlVerified` as `false`, and cleans its package, public certificate, and raw results before publishing a summary. Development acceptance passed in a disposable guest. Smart App Control and public-trust signing remain unverified.

Gate 6 adds deterministic application-side resolution at code head `7990682f`: a fixed 19-field manifest, 15 construction-critical fields, exact source authority, checked GiB conversion, bounded freshness and capture-span rules, closed diagnostics, immutable output, and fail-closed canonical snapshot construction.

Gate 7 activates the x64 product service at code head `19ab9418`. It acquires only fixed verified tools, retains custody through collection and resolution, bounds native work to four operations and external work to one operation, emits seven ordered progress stages, resolves once, maps every terminal state to fixed safe codes, and creates a handoff only from resolved evidence. Its v12 disposable-guest campaign passed 70/70 tests in each of three normally installed package activations. This is development-only evidence: public trust and Smart App Control remain unverified. Gates 8-9 remain responsible for final WinUI/accessibility acceptance and supported Intel-machine end-to-end proof.
